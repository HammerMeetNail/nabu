# PWA and backend review — 10 September 2026

Reviewed commit: `5197f27ef5887859459f75900d6ec69b8530c5da` (`v0.1.355`).

Nabu has a useful foundation for a larger household audience. The direct logging flow, small dependency set, PostgreSQL storage, and existing security controls are worth keeping. The immediate work is to make data entry dependable and household privacy consistent. Several important defects appear only during failed requests, account or household transitions, and historical-data loading; the existing happy-path tests do not catch them.

The disappearing recent-amount chips are reproducible in production. Their contents depend on which other tabs have already loaded logs. They need a stable source independent of Activity search and calendar navigation.

I would repair the P1 privacy and data-loss findings first, then the everyday PWA issues, then measure and improve capacity. The investigation does not establish a household-count limit or show that the current production service is overloaded.

## Privacy and security

### SEC-1 · P1 — Verified sign-in can inherit an attacker's password and sessions

**Local reproduced with a mock verified Google identity; related paths source traced.** Register an unverified account using another person's email and a password known to the registrant. When the email owner later uses verified Google sign-in, Nabu finds the existing account by email and marks it verified. The earlier password and session remain valid. The local probe confirmed both still authenticate as the same account. If the real owner then joins their household, the earlier registrant can access it through that account.

The web Apple linking flow and magic-link flow need the same review. Google/Apple token signature validation itself was not the failure. This is also separate from the explicitly accepted register-auto-login account-existence oracle.

**Fix direction:** define an atomic claim/link flow for unverified accounts. Proof of email ownership must not silently legitimize credentials or sessions established without that proof. Revoke untrusted authentication material when claiming an account, and require appropriate proof before linking established accounts.

**Acceptance:** pre-register an email, retain its session, complete verified sign-in as that email, then prove the old password/session cannot access the claimed account. Cover concurrent claim/login, verified existing accounts, Google, web Apple, magic link, and reset flows.

### SEC-2 · P1 — Removing a member does not revoke their ability to rejoin

**Local PostgreSQL reproduced.** Household responses expose the permanent invite code to members. Removing a member neither rotates that code nor invalidates its use by the removed account. The probe observed removal 200, household access denied, rejoin with the saved code 200, and shared household access restored. Deleting generated invitation records does not revoke this separate code.

**Fix direction:** make revocation cover previously disclosed invitation capabilities. Decide who may invite, use expiring/revocable invitations, and provide rotation or equivalent invalidation. Hiding a code in the UI alone is insufficient.

**Acceptance:** a removed member cannot use a previously learned code or invite to regain access; valid newly issued invitations still work. Preserve atomic one-time invite consumption.

### SEC-3 · P1 — Membership revocation can race with household switching

**Source traced; needs a deterministic PostgreSQL concurrency test.** Switching first reads membership and then writes the user's active household in separate statements. A removal can happen between them, after which the pending switch restores the removed household pointer. A later service recheck can reject the switch without undoing that write. Authentication and legacy role fallback can still treat the stored household/role fields as authority.

**Fix direction:** use canonical current membership for authorization and serialize membership changes with household activation. Commit policy checks and related pointer/role updates atomically; remove unsafe legacy fallback once migrated.

**Acceptance:** pause activation after its membership read, remove membership, resume activation, and verify subsequent authenticated reads and mutations remain denied. Include database-write failure and concurrent ownership-transfer cases.

### SEC-4 · P1 — Idempotency replay can return a log that has become private

**Local PostgreSQL reproduced.** A member logs shared chore A with known key K. An admin makes A private and updates the note. The member then submits visible chore B with K. The handler checks B, while the service returns the old log selected by household/key without authorizing that returned record. **Acceptance:** the sequence above never reveals A; ordinary retry of the same authorized submission still yields exactly one log and one set of side effects.

## Data durability and everyday correctness

### DATA-1 · P1 — Account deletion can partially destroy data and then fail

**Local PostgreSQL reproduced.** Deletion validates memberships, deletes sole households one by one, removes other memberships, and finally deletes the user. These are separate transactions. In the probe, an account with two sole households plus membership and authored content in a surviving household received HTTP 500 after its household count had already fallen from three to two.

The legacy `users.household_id ON DELETE CASCADE` can delete the user during an earlier household delete, before the later cleanup clears references from surviving chores, schedules, and invites. A separate source-traced race allows someone to join between the sole-member check and the household delete, which could cascade into that joining user's account. That race has not been executed.

**Production observation:** deletion of the isolated, single-member audit account also returned 500 and left the account/household present. The matching local singleton with seeded defaults and three logs deleted successfully. The production singleton cause is unconfirmed and must not be attributed to a particular FK without runtime evidence.

**Fix direction:** one transaction for policy checks and all mutations, appropriate household/membership locking, safe cleanup ordering, and migration away from the legacy destructive user-to-household cascade. Add sanitized error diagnostics. Account deletion must have an explicit policy for authored private content, surviving shared content, invitations, notifications, and backups.

**Acceptance:** PostgreSQL tests with all migrations, multiple memberships, surviving authored/assigned content, injected write failures, and a barrier-controlled concurrent join. Failure leaves all original data intact; success removes only the intended account and eligible households.

### DATA-4 · P1 — Offline logs are discarded after authentication errors

**Local browser reproduced for 401; related paths source traced.** A queued log was removed from IndexedDB when replay returned 401; the server never received the log. The code also deletes on 403 and most other 4xx statuses, with no failed-entry recovery UI.

**Fix direction:** scope each queued operation to its account, household, and logical submission; pause for reauthentication/context mismatch; retain recoverable failures and offer retry or deliberate discard. ## Implementation sequence and validation

These are proposed work packages, not changes already made:

1. **Restore privacy boundaries:** SEC-1 through SEC-6, DATA-1, and the membership/notification lifecycle work in SEC-7. Use independent security/persistence review and real PostgreSQL failure/concurrency tests.

3. **Repair navigation, dates, and forms:** UX-3 through UX-6 and DATA-6. Keep daily direct logging fast; make empty/loading/error/pending states truthful and recovery possible.
4. **Prepare for more households:** SEC-9/10, PERF-1/2/3, OPS-1/2/3/4. Establish workload and latency/recovery targets, then measure changes against them.

Every implemented bug fix should first gain a regression at the vulnerable layer and a Playwright reproduction where applicable. Concurrency tests need explicit barriers or deferred responses rather than timing sleeps. Keep a PostgreSQL-backed integration/E2E lane: sqlmock and memory stores cannot expose FK ordering, rollback, query plans, or canonical-membership races. CI already runs Go tests with PostgreSQL available, but most store tests use mocks and the existing E2E CI server uses memory storage.

The 64.2% coverage result is a signal to inspect gaps, not a reason to write tests that mirror implementation. Prioritize cross-household negative cases, failed permission lookups, partial writes, asynchronous response reversal, offline recovery, date boundaries, and real database semantics. Run focused regressions and independent review before the required full build/vet/Go/JS/E2E checks during implementation.

This review does not propose a framework rewrite, microservices, or a new database. Focused modules for identity/context, data loading, and mutation recovery would make the current `app.js` easier to reason about while retaining the existing DOM-oriented frontend.
